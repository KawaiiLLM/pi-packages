# 用量花费改为增量账本

**状态：已实现，合成回归及真实会话目录的注销／重新登记序列验证通过，三个窗口金额与全量扫描一致；完整性能及线上卡顿验收尚未完成。**

用户裁决（2026-09-24，原话）：

> 统计今日会话，难道最优解不是缓存之前的消费，只追加新增的部分吗

> 写一个spec到这个项目位置

**结论：** `pi-usage` 算一次花费，就要把会话日志整个重扫一遍。每轮对话要算三到四次，其中周窗口那次一次就读约 926 MB。每次扫描都会把主线程整块冻住 180–220 ms，这是 Pi 活跃时频繁卡顿的主要来源。

**改法：** 在进程内维护一个花费账本。每个日志文件记住已经读到的字节位置，下次只读新追加的部分。今日、5 小时窗口、周窗口三个金额都从这一个账本求和。

## 问题

### 触发频率

下表列出哪些事件会触发扫描，每次扫描都是 `sumProviderSpend` 的全量扫描：

| 事件 | 触发的扫描 | 起点 |
| --- | --- | --- |
| `turn_start`、`model_select`、`session_tree` | `begin` 一次今日扫描；`publish` 再并行跑 5 小时窗口、周窗口各一次 | 今天零点；窗口起点 |
| `turn_end` | 今日扫描 | 今天零点 |
| 会话开始、零点 | 今日扫描 | 今天零点 |

一次全量扫描的步骤：
1. 递归列出会话目录，给每个文件查修改时间；
2. 把起点之后改过的文件整个读成字符串，按行切分；
3. 对含 `"assistant"` 的行解析 JSON，并用 SHA-256 去重。

新一次刷新会中止上一次，然后从头再扫。也就是说，一轮对话最多触发四次全量扫描。

### 数据量与实测

2026-09-24 在本机测量：
- 会话目录共 27,943 个 `.jsonl` 文件，1.9 GB。
- 当前的长会话单个文件就有 132 MB，三个窗口都覆盖它。

下表是在独立进程里直接调用 `sumProviderSpend` 的结果，主线程卡顿用 10 ms 的心跳测量：

| 扫描 | 读取范围 | 墙钟时间 | 主线程整块卡顿 |
| --- | --- | ---: | --- |
| 今日 | 832 个文件，190 MB | 0.9–1.1 s | 一次，180–190 ms |
| 5 小时窗口 | 近 5 小时改过的文件 | 0.77 s | 一次，201 ms |
| 周窗口（按近 7 天估算） | 10,712 个文件，926 MB | 4.8 s | 两次，219 ms 和 62 ms |

整块卡顿来自把 132 MB 的文件一次解码成字符串，再整体切行。

这个 132 MB 的长会话里各行有多长：

| 类型 | 条数 | 最长 | 单行代价 |
| --- | ---: | ---: | --- |
| 全部行 | 54,100 | 2.49 MB | 有 4 行超过 1 MiB，都不是计费回复，只会做一次字符串查找 |
| 计费回复 | 8,604 | 132 KB（99 分位 29 KB） | 解析加算去重键，最长一行 0.46 ms |

### 线上 Pi 的表现

以下证据来自 Trace Memory 的调试插桩、对运行中 Pi 的采样和打开文件的检查：
- **卡顿频率：** Pi 活跃时，平均每分钟约 33 次主线程卡顿（比心跳间隔多出 100 ms 以上）。多出部分的中位数是 180 ms。
- **不是 Trace Memory：** 其中 94% 不落在 Trace Memory 任何计时过的调用里。
- **CPU 花在哪：** 对运行中的 Pi 采样 8 秒，主线程约 65% 的时间在处理文件读取完成后的回调。热点依次是 UTF-8 解码、按换行切分、字符串查找、JSON 解析、SHA-256、目录遍历和查询文件信息，和 `sumProviderSpend` 的步骤一一对应。
- **在读什么：** 同一时刻用 `lsof` 查看，它正在依次打开不同会话的日志。

## 方案：进程内的花费账本

`pi-usage` 只持有一个账本，三个金额都从它读。下面的接口形状是提议，名字待定：

```ts
type SpendPurpose = "today" | "fiveHour" | "weekly";

interface SpendLedger {
  /** Bring the ledger up to date for one purpose's window start. Concurrent callers share passes. */
  update(purpose: SpendPurpose, sinceMs: number, signal?: AbortSignal): Promise<void>;
  /** Forget a purpose that is no longer shown, such as a window of a provider that has none. */
  release(purpose: SpendPurpose): void;
  /** Sum of the deduplicated replies of one provider at or after sinceMs. */
  sum(providerId: string, sinceMs: number): number;
  /** Abort the running pass. The ledger's data is kept for the rest of the process. */
  stop(): void;
}
```

- 今日金额是 `sum(provider, 今天零点)`。
- 5 小时和周窗口是 `sum(provider, usageWindowStart(window))`。

### 账本记什么

账本分两层记录，都只存计费需要的字段：
- **每个文件：**
  - inode、大小、修改时间；
  - 已经消费到的字节位置；
  - 这个位置之前的最后 64 字节，作为指纹；
  - 这个文件里出现过的计费回复的去重键；
  - 文件末尾没有换行符那段临时计入的回复（如果有），见「增量读取」第 3 步。
- **每条计费回复（按去重键只存一份）：**
  - 时间、provider、金额；
  - 它出现在几个文件里（引用计数）。
  - 不存回复原文。
- **保留下限：** 所有用途最近一次请求的起点中最早的那个。它决定哪些回复值得保留，详见「清理」一节。

**去重键的定义不变：** `sha256(JSON.stringify([entry.id, entry.timestamp, entry.message]))`。分叉出来的会话会复制旧回复，这些回复仍然只计一次；因为复制品连时间戳都相同，所以按时间过滤时也不会出错。

**没有字符串类型 `entry.id` 的回复不参与去重。** 现有实现对这种回复每出现一次就计一次费。账本给每次出现单独生成一个键（文件的 inode 加这一行在文件里的字节位置），所以同样每次都计费；文件重置时，这些键随旧记录一起被替换掉。

**为什么要引用计数：** 某个文件被重置或删除时，只撤回它自己的引用。同一条回复如果还出现在另一个文件里，就继续计费，不会被误删。

### 支持哪些文件变化

以下依据已安装 Pi 0.87.1 的 `dist/core/session-manager.js`：
- **追加：** 新条目用 `appendFileSync` 写到文件末尾。修复没写完的最后一行时，也只是在末尾补一个换行符。
- **整文件重写：** `_rewriteFile` 以截断方式打开同一个文件（inode 不变），把全部条目重新序列化写一遍。只在两种情况下发生：加载时需要升级格式、打开的是一个空文件。
- **分叉：** 分叉出的会话写进一个新文件，不改动原文件。

更新时按下表判断每个文件（修改时间早于本次请求起点的文件不读，它们不可能含有起点之后的回复）：

| 观察到的状态 | 处理 |
| --- | --- |
| 账本里没有这个文件 | 从位置 0 读 |
| inode 变了 | 重置（做法见表后） |
| 大小小于记录的位置 | 重置 |
| 大小等于位置，修改时间也没变 | 跳过，不做任何读取 |
| 大小等于位置，但修改时间变了 | 说明文件被原地改过，但不是追加（只可能是格式升级），重置 |
| 大小大于位置 | 先读回位置之前的 64 字节核对指纹：不符则重置，相符则只读追加的部分 |
| 确认已删除：它路径上的某一级目录这次读取成功，而下一级（子目录或文件本身）不在列表里；或者读目录、查文件信息时得到「不存在」（`ENOENT`） | 撤回它的全部引用。整个子目录被删除时，其下所有文件一并撤回 |
| 无法确认：读目录、查文件信息或读文件时遇到其他错误（例如 `EMFILE`、`EACCES`、`EIO`） | 不当作删除，保留原有记录，本轮沿用它上次成功读到的贡献，见下文「读取失败」 |

**重置的做法：先建新记录，成功后再替换。**
- **重读：** 从位置 0 把文件重读成一份新记录。读的过程中不影响账本，求和仍用旧记录。
- **替换：** 整个文件读完且全部成功后，在同一次提交里撤回旧记录的引用、加入新记录。
- **中途出错：** 如果读取失败或这一轮被停下，丢弃新记录、保留旧记录，下一轮再重试。这样重置遇到读取失败时，仍然能沿用上次成功读到的贡献（见下文「读取失败」）。
- **与追加的区别：** 普通的追加读取仍然按块提交，不走这套。

**读取失败：** 这是本方案唯一有意偏离现有实现的地方。
- **现有实现：** 读不了的目录或文件直接跳过，本轮按 0 计。例如某个文件上次贡献了 $10，这次因为一时打开文件过多（`EMFILE`）读失败，今日金额就凭空少了 $10。
- **账本：** 沿用这个文件上次成功读到的贡献，下次读取成功时再更新。一次偶发的读取错误，不应该让显示的金额往下跳。claude-powerline 也有同样的考虑：解析失败的结果不写进缓存，以免偶发错误（比如并发读取时文件打开过多）污染缓存。
- **不新增错误标记：** 快照接口保持不变。现有实现遇到这种失败也不报错。

**范围之外：** 一次原地改写既让文件变大，又改了已消费的内容，同时恰好让位置之前那 64 字节不变——这种情况检测不到。Pi 自己的重写会把所有条目重新序列化，内容要么逐字不变，要么整体移位，不会出现这种形态。手工编辑会话文件不在支持范围内；重启进程会从头重算。

### 增量读取

1. **从记录的位置读到文件末尾**，按块读，每块最多 1 MiB。每读完一块就把控制权交还给事件循环。
2. **行可以跨块。** 一块读完、末尾那行还没遇到换行符时，把这段未完成的字节带到下一块，继续拼接，直到遇到换行符。超过 1 MiB 的行也就这样在同一次更新里读完，不会一直拖到下次刷新。
3. **文件末尾没有换行符的那段，每轮都重读，并按现有实现的规则处理。**
   - 已提交的位置只推进到以换行符结尾的行，这一段不算进去，所以每一轮都会从这段的开头重新读它。
   - 如果它能完整解析成一条计费回复，就在本轮临时计入，并替换这个文件上一轮临时计入的那条。
   - 这和现有实现一致：现有实现会给最后一行计费，即使它没有换行符，现有测试里也有这种文件。
   - 下一轮如果这一行继续被写长，就按拼接后的整行重新判断。例如被写成了两段 JSON 连在一起、无法解析，临时计入的那条就撤回，同样和现有实现一致。
   - 等它补上了换行符，就转为正式计入。撤回临时的那份、加入正式的那份，在同一次提交里完成：这条回复只计一次，也不会碰到其他分叉文件对同一条回复的引用。
     - 对没有字符串 `id` 的回复，临时和正式用的是同一个键，因为这一行在文件里的字节位置不变。
   - Pi 写每条记录时都连同换行符一起写入，所以正常情况下这一段是空的，没有重读开销。
4. **按字节切分：** 未完成的行以原始字节的形式带着走，只在换行处解码。UTF-8 中换行符的字节 `0x0A` 不会出现在多字节字符内部，不会把一个字截断。
5. **每块原子提交。** 一块里所有完整的行解析出来的回复，连同新位置、新指纹，一起写入账本。中途停下时，只丢掉还没提交的那一块；下次从已提交的位置继续。

### 并发与取消

- **同一时刻只跑一轮读取。** 每轮读取覆盖它开始时账本的保留下限。
- **每个请求都要等到一轮在它之后才开始的读取。** 正在进行的那一轮不能满足它：那一轮可能已经读过当前会话的文件，而这个请求正是因为刚追加了新回复才发出的。
  > 例：一轮读取刚读完当前会话的文件、正在读别的文件，此时当前会话追加了一条计费回复并触发 `turn_end` 刷新。如果这个刷新并入正在跑的这一轮，这轮结束时它拿到的金额里没有那条新回复。
- **合并规则：**
  - 读取进行中到达的请求，全部合并进紧接着的下一轮，排队的最多一轮。
  - 同时到达、且都在一轮开始之前的请求，共用那一轮。例如 `turn_start` 同时请求今日、5 小时、周窗口，只读一轮。
  - 请求的起点早于当前保留下限时，先降低下限，下一轮就按新的下限读。
- **调用者取消只影响它自己的等待：** 它的 `update` 以 `AbortError` 结束，但共享的那轮读取照常进行，其他等待者不受影响。
- **只有账本自己的 `stop()` 会中止读取**，例如会话关闭时。普通追加保留已提交的块，只丢弃尚未提交的部分；重置重读则丢弃整份未提交的新记录，保留旧记录。
- **账本随进程存在，不随会话存在。** 一个进程只有一个账本（每个会话目录一个）。`stop()` 只中止正在进行的那一轮读取，不丢弃任何数据；会话关闭、`/new`、`/resume` 之后接着用同一个账本，下一轮只读新增的部分。
- **替换现有逻辑：** 现在「新刷新中止旧扫描」的做法取消。各刷新器现有的「结果是否仍然有效」检查（会话、模型、日期）保留，照旧丢弃过期结果。

### 清理

- **保留下限怎么算：** 账本按用途记住每个用途最近一次请求的起点，保留下限取其中最早的一个。不再显示的用途（例如切换到没有窗口的 provider）通过 `release` 注销。
- **注销不会让下限后移。** 下限只在一种情况下后移：一个仍在登记中的用途，它自己的起点随时间变晚（例如过了零点，或 5 小时、周窗口向前滚动）。注销一个用途、重新登记一个用途，都不触发撤回。
  > 例：换模型时，`begin` 先注销今日、5 小时、周三个用途，接着单独刷新一次今日。如果注销或单独刷新会让下限后移，账本会把今天以前的回复全部撤回，紧接着周窗口重新登记时，只能整周重读（实测约 3.3 秒）。按本条规则，这时什么都不撤回。
- **从没撤回过时，读入全部记下；撤回过之后，读入也守同一条边界：**
  - 还从没撤回过时，读一个文件就把其中的计费回复全部记下，不按下限过滤。
  - 保留下限往后移时（按上一条，只有仍在登记中的用途起点随时间变晚），撤回时间早于新下限的回复，并记下「已撤回到哪里」。这些回复不会影响任何起点不早于新下限的求和；分叉复制品的时间戳相同，会一并撤回。
  - 撤回过之后，再读入的回复（包括新分叉文件复制过来的旧历史），时间早于「已撤回到的位置」的直接跳过。否则这些过期回复会被重新带回，而且只要下限不再移动，就会一直留着。
  - 文件的读取位置照旧保留，不会因此重读。
  - 这样就能处理一直在追加的长会话：它的修改时间永远是最新的，但其中的旧回复会随下限后移被撤回。稳定后，账本里只剩近一周（周窗口）以内的计费回复，估计几万条、几 MB，需要实测。
- **下限往前移：**
  - 新下限不早于「已撤回到的位置」（或者还从没撤回过）：已跟踪的文件里，需要的回复都还在，只需补读新落入范围的文件。进程启动时，今日、5 小时、周窗口先后到达，就属于这种情况，不会重读已经读过的文件。
  - 新下限早于「已撤回到的位置」：比如换到一个周窗口开始得更早的账号。已撤回的回复补不回来，于是所有文件重置，分块重新读一遍。这种情况很少。
- **文件删除：** 只在确认删除时撤回，包括整个子目录被删的情况，判断规则见「支持哪些文件变化」一节的表。遍历中途停下的那一轮不撤回任何文件。

### 首次读取

- **进程刚启动时：** 第一次更新要把范围内的文件从头读一遍，按周窗口算约 926 MB。
- **分块的作用：** 这次读取不会再整块冻住主线程，但总耗时仍是秒级，在后台完成。
- **之后：** 每轮只读新增的部分。

**分块不等于卡顿一定低于 50 ms。** 一块里的解码、切行、查找和解析，都是连续执行、中间不让出主线程的同步工作。按实测，最长的计费回复解析加算键只要 0.46 ms，1 MiB 的块预计是毫秒级；但这要在验收里实测确认，不能当作前提。

## 参考与被否决的做法

- **claude-powerline**（`~/Projects/claude-powerline/src/utils/transcript-cache.ts`）
  - 它的做法：
    - 按文件把解析结果缓存到磁盘，以路径、修改时间和大小作为键，文件一变就整个重新解析；
    - 另有一个整体结果缓存，所有日志里最新的修改时间一变就失效。
  - 它这样设计的原因：状态栏每次渲染都是一个新进程，只能靠磁盘缓存。它跑在独立进程里，重新解析也不会冻住 CC 的界面。
  - 为什么不照搬：`pi-usage` 每轮仍要把正在写的 132 MB 文件整个重新解析，卡顿不会消失。
  - 本方案沿用它「按文件缓存、只存计费字段」的思路，但把失效规则从「一变就整个重解析」推进到「只读追加的部分」。
- **磁盘缓存：** 能省掉进程启动时那次首读，代价是多一套磁盘缓存的失效与清理逻辑。进程常驻时，它只在启动那一次有用。先不做，实测首读的影响后再决定。
- **节流**（例如最多每 30 秒刷新一次）：每次仍是全量扫描，卡顿只是变少，没有消失，不解决根因。
- **只累加当前会话在内存里的回复：** 看不到子任务会话、其他 Pi 窗口的花费。
- **用目录监听代替每次遍历**（`fs.watch`）：能省掉每轮约 2.8 万次文件信息查询。遍历是异步的，不会整块冻住主线程。先实测它的开销，明显再做。
- **对已消费内容做完整校验**（例如把已读过的部分整体算一个哈希）：每次核对都要把整个文件重读一遍，等于退回全量扫描。本方案改为依据 Pi 实际的写入方式，定义清楚支持哪些文件变化。

## 不做

- **不改计费口径：** 哪些回复计费、金额取 `usage.cost.total`、按 provider 和时间过滤、去重键的定义，全部保持不变。
- **不改对外接口：** 快照入口 `@narumitw/pi-usage/snapshot` 和状态栏的渲染都不动。
- **不做磁盘缓存和目录监听**，原因见上一节。

## 验收

- **与全量扫描等价。**
  - 用临时会话目录跑随机操作序列，覆盖以下情况：
    - 追加完整行；
    - 追加半行、之后补全；
    - 超过 1 MiB 的单行；
    - 多字节字符正好跨在块边界上；
    - 分叉复制旧回复；
    - 截断后重写成更长、一样长、更短的内容；
    - 替换文件（inode 变化）；
    - 新增文件、删除文件、删除整个子目录；
    - 跨过零点；
    - 保留下限前移和后移，以及撤回之后才出现、复制了旧历史的分叉文件；
    - 最后一行是完整 JSON 但没有换行符，之后又被续写，或者补上换行符转为正式计入；
    - 没有字符串 `id` 的回复多次出现，包括它正处在末尾、没有换行符的时候。
  - 每一步之后，只要这一步的所有读取都成功，三个金额都与现有 `sumProviderSpend` 的结果相等，允许浮点误差小于 1e-9 美元。
- **读取失败：** 注入目录、查文件信息、读文件三种失败。账本给出的金额，等于把读失败的文件按上次成功读到的内容计算时，现有实现会得到的金额。失败的文件不会被当作删除；恢复读取后，金额与现有实现一致。
- **重置后读取失败，再恢复：** 文件先被截短或替换、触发重置，重读时出错。这期间金额沿用旧记录；恢复读取后换成新记录，金额与现有实现一致。重读中途被停下时同样如此。
- **临时计入转正：** 一条没有换行符的完整回复，先被临时计入，再补上换行符。整个过程中它只计一次；如果另一个分叉文件里也有同一条回复，那个文件的引用保持不变。这项分别测带字符串 `id` 和不带的两种回复。
- **读取量，分四项计：**
  - **新增数据：** 一次普通刷新读取的追加字节数，恰好等于上次刷新以来追加的字节数；没变化的文件为零。
  - **校验开销：** 每个变大的文件最多多读 64 字节，单独统计。
  - **未完成行的重读：** 文件末尾没有换行符的那段，每轮都会重读，单独统计。正常的 Pi 会话里它应为零。
  - **重置重读：** 单独计数，并注明原因（哪一种变化）。
  - 以上用对 `FileHandle.read` 的计数来断言。
- **并发与取消。**
  - 刷新中途停下后，下一次刷新从已提交的位置继续，金额正确。
  - 三个窗口同时请求时，只有一轮读取。
  - 读取进行中追加了新回复并发来刷新请求，这个请求拿到的金额里包含那条新回复；多个这样的请求只多跑一轮。
  - 撤回之后读入的旧历史回复不会留在账本里。
- **注销与会话切换不引起重读。**
  - 依次注销今日、5 小时和周窗口，再单独刷新今日，然后重新登记 5 小时和周窗口：整个过程不撤回任何回复，也不重读任何文件，读取量只有新增部分。
  - 同一进程里关闭会话再开新会话（`stop()` 之后再用），也是如此。
  - 过了零点、窗口向前滚动时，照常撤回早于新下限的回复。
  - 某个调用者取消，只结束它自己的等待，其他等待者照常拿到结果。
- **内存：** 一直在追加的长会话，经过下限后移之后，账本里只保留下限之后的回复。
- **本机实测：** 在真实会话目录上报告以下数据：
  - 稳态刷新（只追加几 KB）的墙钟时间，以及主线程最长的一次连续执行，不应超过 50 ms；
  - 首次读取的墙钟时间、最长连续执行（提议上限 50 ms）、账本条数和内存占用；
  - 最长的一块、最长的一行各自的处理时间。
- **线上 Pi 实测：** 用同样的心跳，对比改动前后活跃时每分钟的卡顿次数和卡顿时长的中位数。
- **集成检查：**
  - `pnpm check`、`pnpm test`、`pnpm test:integration` 全部通过；
  - 同步更新 `UPSTREAMS.md` 里 `pi-usage` 的本地差异说明。日志金额扫描是从状态栏迁入的本地实现。
